# Risk Assessment & Mitigation Strategies

本文档旨在识别 "Us & Me" 项目在开发、产品和运营过程中可能面临的风险，并提供相应的缓解策略。

## 1. 技术风险 (Technical Risks)

### 1.1 Supabase Realtime 连接与限制
*   **风险描述**: 免费版 Supabase 对并发连接数和消息传输量有限制。在网络不稳定情况下，Realtime 连接可能断开，导致点餐通知无法送达。
*   **影响**: 高。核心功能“实时点餐通知”失效，用户体验严重受损。
*   **缓解策略**:
    *   实现**客户端轮询 (Polling)** 作为降级方案（例如每 30 秒检查一次新订单）。
    *   增加**连接状态监听**，在 UI 上提示“网络连接中断”。
    *   使用乐观 UI (Optimistic UI) 更新，减少对服务器响应的依赖感。

### 1.2 PWA 在 iOS 上的局限性
*   **风险描述**: iOS 对 PWA 的支持不如 Android 完善，特别是 Web Push Notifications (推送通知) 配置复杂，且依赖用户将应用添加到主屏幕。
*   **影响**: 中。用户可能错过重要通知。
*   **缓解策略**:
    *   在 Onboarding 流程中，引导用户**必须**将 App 添加到主屏幕。
    *   使用短信或邮件作为备用通知渠道（视成本而定）。
    *   依靠应用内红点/弹窗作为主要交互提示。

### 1.3 图片存储与加载性能
*   **风险描述**: 菜品图片和日记照片可能占用大量带宽和存储空间，导致加载缓慢和成本上升。
*   **影响**: 中。页面卡顿，流量消耗大。
*   **缓解策略**:
    *   **客户端压缩**: 上传前在浏览器端对图片进行压缩（如 `browser-image-compression`）。
    *   **CDN 缓存**: 利用 Supabase Storage 自带的 CDN 功能。
    *   **懒加载**: 列表页图片全部采用 Lazy Load。

## 2. 产品风险 (Product Risks)

### 2.1 经济系统失衡 (积分通胀)
*   **风险描述**: 如果“赚取积分”的任务过于简单，而“消费积分”的途径太少，用户会积累大量无处使用的积分，导致激励失效。
*   **影响**: 高。游戏化机制崩溃，用户失去动力。
*   **缓解策略**:
    *   **动态定价**: 允许大厨根据心情调整菜品价格。
    *   **消耗大户**: 引入“兑换券”或“免做家务卡”等高价值消耗品。
    *   **定期重置**: 考虑按月或季度重置部分积分，或举办“赛季”。

### 2.2 双边活跃度不对等
*   **风险描述**: 情侣应用常见问题，一方热衷记录，另一方冷淡，导致活跃方最终放弃。
*   **影响**: 致命。用户流失。
*   **缓解策略**:
    *   **极简操作**: 即使是被动方，点击“接单”或“点赞”的操作成本必须极低。
    *   **情感反馈**: 当一方完成操作时，给予强烈的视觉反馈（撒花、动画），提供情绪价值。

### 2.3 隐私界限模糊
*   **风险描述**: 用户可能误将私密内容发到 We Mode，或者担心 Me Mode 内容被数据库管理员（你）看到。
*   **影响**: 中。信任危机。
*   **缓解策略**:
    *   **UI 区分**: We/Me 模式采用截然不同的配色（绿 vs 紫），从视觉上强力暗示当前环境。
    *   **二次确认**: 发布私密内容时增加 Toast 提示“仅自己可见”。

## 3. 项目管理风险 (Project Management Risks)

### 3.1 范围蔓延 (Scope Creep)
*   **风险描述**: 在开发过程中不断想加新功能（如“聊天”、“日历”），导致 MVP 迟迟无法上线。
*   **影响**: 高。项目延期，士气低落。
*   **缓解策略**:
    *   **严格遵守 Master PRD**: 任何新想法都先放入 Backlog (Icebox)，坚决不插入当前 Sprint。
    *   **Timeboxing**: 为每个阶段设定严格的时间盒（如 Phase 1 必须在 3 天内结束），功能没做完也强制进入下一阶段或削减功能。

### 3.2 UI 风格实现难度
*   **风险描述**: “新粗野主义”风格非常依赖 CSS 细节（硬阴影、边框），Shadcn 默认组件需要大量魔改，可能耗费过多时间在样式上。
*   **影响**: 中。开发效率降低。
*   **缓解策略**:
    *   **组件封装**: 先花时间封装一套基础的 `NeoButton`, `NeoCard`，磨刀不误砍柴工。
    *   **妥协**: 遇到难以实现的复杂动效，优先保证功能可用，样式后期迭代。
