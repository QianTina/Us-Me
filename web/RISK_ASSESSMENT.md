# 项目风险评估文档 (Risk Assessment)

本文档旨在评估 "Us & Me" 情侣生活 OS 项目的潜在风险，并提出相应的缓解策略。

## 1. 技术风险 (Technical Risks)

### 1.1 Supabase 依赖性
*   **风险描述**: 项目深度依赖 Supabase (Auth, Database, Realtime, Storage)。如果 Supabase 服务中断或 API 发生重大变更，可能导致应用不可用。
*   **缓解策略**:
    *   定期备份数据库 Schema 和关键数据（虽然 Supabase 有自动备份，但建议手动导出 SQL 脚本）。
    *   保持 `supabase-js` 客户端库的更新，关注官方变更日志。
    *   考虑在未来引入本地优先 (Local-first) 架构（如 RxDB），仅将 Supabase 用作同步后端。

### 1.2 实时连接限制 (Realtime Limits)
*   **风险描述**: Supabase Realtime 的免费层级有并发连接数限制。虽然对于情侣（2人）应用不是问题，但如果通过“家庭”概念扩展用户群，可能触及限制。
*   **缓解策略**:
    *   监控 Realtime 连接状态，处理断线重连逻辑。
    *   对于非关键实时数据（如统计面板），降级为轮询 (Polling) 或手动刷新。

### 1.3 客户端性能
*   **风险描述**: 随着订单和任务日志的积累，前端一次性拉取大量数据可能导致卡顿。
*   **缓解策略**:
    *   已在关键查询中实施分页 (`.limit(20)`)。
    *   对于统计数据，未来应考虑在数据库层面创建视图 (View) 或定时任务计算汇总数据，而不是在前端计算。

## 2. 安全风险 (Security Risks)

### 2.1 积分系统漏洞 (Points Inflation)
*   **风险描述**: 恶意用户可能通过篡改前端代码或直接调用 API 来给自己刷分。
*   **缓解策略**:
    *   **关键逻辑后端化**: 目前已将积分扣除 (`place_order`) 和积分奖励 (`approve_chore`) 逻辑封装在 PostgreSQL RPC 函数中，并标记为 `SECURITY DEFINER`。
    *   **严格的 RLS**: 确保用户只能修改自己的数据，且只有“家庭成员”才能审批任务。
    *   **输入验证**: 后端函数中增加了对负数积分、余额不足等情况的检查。

### 2.2 数据隔离失效
*   **风险描述**: 既然是多租户系统（通过 `family_id` 隔离），RLS 配置错误可能导致一个家庭看到另一个家庭的数据。
*   **缓解策略**:
    *   所有 RLS 策略必须强制检查 `family_id`。
    *   在开发过程中反复进行跨用户、跨家庭的测试。
    *   使用 `supabase_schema_consolidated_v19.sql` 中的脚本确保 RLS 策略覆盖所有表。

## 3. 产品与设计风险 (Product & Design Risks)

### 3.1 游戏化疲劳 (Gamification Fatigue)
*   **风险描述**: 长期使用后，用户可能对“赚积分-花积分”的模式感到厌倦，导致应用闲置。
*   **缓解策略**:
    *   引入“愿望券” (Wish Coupons) 等高价值、情感化的兑换项（已通过 Store 页面实现）。
    *   定期更新 UI 主题或推出节日限定菜品/任务。
    *   增加“成就系统”或“年度回顾”功能。

### 3.2 审批流程摩擦
*   **风险描述**: 每次任务都需要对方审批可能显得繁琐，引发伴侣间的摩擦。
*   **缓解策略**:
    *   允许“自动审批”规则（未来功能）。
    *   UI 上增加“一键催办”或“撒娇”功能，化解僵硬的审批流程。
    *   目前已在测试模式下支持“自审批”，方便单人体验。

## 4. 维护与运营风险 (Maintenance Risks)

### 4.1 数据库 Schema 漂移
*   **风险描述**: 多次手动修改数据库导致 Schema 混乱，新环境难以复现。
*   **缓解策略**:
    *   **严格的版本控制**: 所有数据库变更是通过编号的 SQL 脚本 (`v1` - `v19`) 管理的。
    *   **Schema Consolidation**: 定期合并 SQL 脚本（如 `v19`），保持 Schema 清洁。
    *   禁止在生产环境直接通过 GUI 修改表结构，必须通过 SQL 脚本执行。

### 4.2 部署环境差异
*   **风险描述**: 本地开发环境与 Vercel 生产环境的环境变量配置不一致。
*   **缓解策略**:
    *   使用 `.env.example` 明确列出所需变量。
    *   部署前检查 `NEXT_PUBLIC_SUPABASE_URL` 和 `NEXT_PUBLIC_SUPABASE_ANON_KEY`。

## 5. 总结

目前的架构设计已针对核心的安全风险（积分安全、数据隔离）采取了强有力的措施（RPC + RLS）。未来的风险主要集中在用户体验的持久性上。建议在功能开发完成后，重点关注 UI 的趣味性和互动细节。
